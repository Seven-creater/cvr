# 项目进度总结（2026-04-16）

## 1. 项目现在在做什么

这个项目的目标，是做一个“视频检索 + AI 复核”的实验系统。

简单说，就是两步：

1. 先用论文里的原始检索方法，找出一批最可能的结果。
2. 再让一个能看视频的模型去复核这些结果，看能不能把检索效果再往上推一点。

这里有两个常见缩写：

- `T2V`：`Text-to-Video`，也就是“文字找视频”
- `V2T`：`Video-to-Text`，也就是“视频找文字”

这里的 `Agent` 可以理解成一个小控制器。它不直接做底层检索，而是负责决定：

- 先看哪些候选结果
- 要不要继续看更多候选
- 什么时候提交最终答案

## 2. 这段时间已经做成了什么

### 2.1 已经把技术路线拉回到论文原始方法

项目一开始走过一条错误路线：自己导出特征、自己做相似度计算。这条路线后来确认并不是真正复现论文方法。

后面已经完成了一次比较大的纠偏：

- 停掉旧的粗检索主线
- 改成直接复用 **AVIGATE 论文复现代码的官方检索链**

这一步的意义非常大，因为它先解决了一个根本问题：

> 我们后面的实验，终于建立在论文原始方法上，而不是建立在一个“看起来像、其实不是”的底座上。

### 2.2 官方检索已经被封装成当前仓库能直接调用的入口

现在仓库里已经有一套“官方 AVIGATE 检索封装”，可以直接做：

- 文字输入，返回 `top-k` 视频
- 视频输入，返回 `top-k` 文本
- 直接计算整套检索指标

也就是说，论文方法本身已经不再是散在复现仓库里的脚本，而是被整理成了当前项目的正式代码入口。

### 2.3 Omni 复核链路已经打通

后面又花了很多时间，把“能看视频的模型”这层打通了。

这个过程里遇到过：

- Python 包版本冲突
- `vllm` / `vllm-omni` 环境混乱
- GPU 残留进程占显存
- 请求格式不对
- 模型不按要求返回结构化 JSON

这些问题现在基本都已经解决。当前已经能稳定做到：

- 本地视频送进 Omni 服务
- 服务正常响应
- 返回结构化结果

这层现在在代码里叫 `Omni Checker`。你可以把它理解成一个“二次裁判”。

### 2.4 单条 official-agent case 已经跑通

在官方检索跑通之后，单条 case 也已经做通了：

- `T2V official-agent case`
- `V2T official-agent case`

这说明整条链已经是通的：

- 官方检索能跑
- Checker 能跑
- Agent 决策能跑
- 能从输入一路走到最终提交

换句话说，端到端实验链路已经建立起来了。

## 3. 当前最重要的结果数据

## 3.1 官方 AVIGATE baseline

服务器上用真实模型和真实数据跑出来的官方 baseline 是：

```json
{
  "dataset": "MSRVTT",
  "video_count": 1000,
  "text_count": 1000,
  "audio_available": true,
  "t2v": {
    "R@1": 0.464,
    "R@5": 0.732,
    "R@10": 0.827
  },
  "v2t": {
    "R@1": 0.435,
    "R@5": 0.723,
    "R@10": 0.819
  }
}
```

这里的 `R@1 / R@5 / R@10` 可以简单理解成：

- 正确答案有没有出现在前 1 个结果里
- 正确答案有没有出现在前 5 个结果里
- 正确答案有没有出现在前 10 个结果里

### 和论文/复现对照结果的比较

按我们当前项目里已经核过的一组论文/复现对照值，MSRVTT 上大致是：

| 方向 | 论文/复现对照值 | 当前官方 baseline | 差值 |
|---|---:|---:|---:|
| T2V R@1 | 0.461 | 0.464 | +0.003 |
| T2V R@5 | 0.730 | 0.732 | +0.002 |
| T2V R@10 | 0.825 | 0.827 | +0.002 |
| V2T R@1 | 0.432 | 0.435 | +0.003 |
| V2T R@5 | 0.720 | 0.723 | +0.003 |
| V2T R@10 | 0.815 | 0.819 | +0.004 |

这张表的意义非常明确：

> 当前仓库里的“官方检索底座”已经和论文/复现结果高度对齐，误差只在 0.5 个百分点以内。

所以到这一步，我们可以放心地说：

- 底层 AVIGATE 检索没有跑偏
- 后面 Agent 做不做得好，问题不在底座，而在 Agent 和 Checker 这一层

## 3.2 单条 official-agent case 的情况

单条 case 方面，目前已经确认：

也就是说，当前系统已经不只是“baseline 能跑”，而是：

## 3.3 V2T 小样本 agent 实验结果

这部分是目前最关键、也是最诚实的一块。

我们已经做过多轮 `V2T` 小样本实验，核心对比如下。

### 旧版 V2T（20 条）

```json
{
  "runs": 20,
  "round1_recall": {
    "R@1": 0.45,
    "R@5": 0.8,
    "R@10": 0.8
  },
  "final_recall": {
    "R@1": 0.45,
    "R@5": 0.5,
    "R@10": 0.5
  },
  "avg_rounds": 2.15,
  "avg_checker_calls": 4.3,
  "retry_rate": 0.65,
  "submit_top1_rate": 0.35,
  "submit_top2_rate": 0.2,
  "mode": "v2t"
}
```

这个结果说明：

- 第一轮官方检索其实已经把很多正确答案放进前 5 / 前 10
- 但 Agent 复核之后，反而把结果做差了

### 新版 V2T（20 条，延迟提交策略）

后面我们试过让 Agent “先多看几个候选，再决定提交”，也就是所谓的“延迟提交”。

最终 20 条完整结果是：

```json
{
  "runs": 20,
  "round1_recall": {
    "R@1": 0.45,
    "R@5": 0.8,
    "R@10": 0.8
  },
  "final_recall": {
    "R@1": 0.45,
    "R@5": 0.5,
    "R@10": 0.5
  },
  "avg_rounds": 3.0,
  "avg_checker_calls": 6.0,
  "retry_rate": 1.0,
  "submit_top1_rate": 0.75,
  "submit_top2_rate": 0.1,
  "mode": "v2t"
}
```

### 旧版和新版的直接对比

| 指标 | 旧版 V2T | 新版 V2T | 变化 |
|---|---:|---:|---:|
| R@1 | 0.45 | 0.45 | 持平 |
| R@5 | 0.50 | 0.50 | 持平 |
| R@10 | 0.50 | 0.50 | 持平 |
| avg_rounds | 2.15 | 3.00 | 变高 |
| avg_checker_calls | 4.3 | 6.0 | 变高 |
| retry_rate | 0.65 | 1.0 | 变高 |

这张表说明了一件很重要的事：

> “更谨慎一点再提交”没有真正解决问题，只是让计算成本更高了。

换句话说：

- 新策略没有把指标拉上去
- 但把轮数和 Checker 调用次数都拉高了

## 3.4 V2T 与论文 baseline 的差距

如果把当前 `V2T agent` 和论文/官方 baseline 放在一起看，会更清楚：

| 指标 | 论文/官方 baseline | 当前 V2T agent 最终结果 |
|---|---:|---:|
| R@1 | 0.435 | 0.45 |
| R@5 | 0.723 | 0.50 |
| R@10 | 0.819 | 0.50 |

这里要注意一个事实：

- `R@1` 看起来不差
- 但 `R@5 / R@10` 明显更低

这说明当前 Agent 的问题不是“完全找不到正确答案”，而是：

> 第一轮检索已经把很多正确答案放进前几名了，但 Agent 没能可靠地把它们保下来，或者没能从 top-k 里稳定挑出正确那个。

## 4. 当前已经确认的结论

### 4.1 已经确认有效的部分

这些事情现在已经算是明确做成了：

- 官方 AVIGATE 检索链已经接进当前仓库
- 官方 baseline 能在服务器上稳定跑出结果
- 和论文/复现对照值高度接近
- Omni Checker 服务已经打通
- 单条 official-agent case 已经跑通
- 小样本 partial eval 命令已经支持边跑边写 `summary.json` 和 `traces.jsonl`

### 4.2 已经确认没有做出提升的部分

目前最重要的负面结论是：

> 当前版本的 `V2T agent` 还没有带来指标提升。

具体来说：

- 没有提升 `R@5`
- 没有提升 `R@10`
- 试过“延迟提交”之后，结果还是没有改善

### 4.3 当前最可能的瓶颈

现在看，真正的问题不再是“代码跑不通”，而是“策略没有打中关键点”。

当前最可能的瓶颈有两个：

1. **Checker 判断不够稳**
   - 该放行的正确候选，有时没放行
   - 不该放行的候选，有时又被放行

2. **Agent 现在是逐个候选判断**
   - 它更像是在回答“这一个像不像”
   - 但真正需要的，更像是“这 6 个里谁最好”

这两个问题叠在一起，会导致：

- 正确答案明明在前几名里
- 但 Agent 还是没把它稳定地挑出来

## 5. 项目整体做到什么程度了

如果把整个项目分成几个阶段，现在大概是这样：

### 已完成

- 正确的论文检索底座已经接好
- 服务器上的真实模型和真实数据已经跑通
- 检索、Checker、单条 Agent 链路都能工作
- 小样本评测工具已经做好

### 已验证但结论偏负面

- 当前版本的 `V2T agent` 没有带来指标提升
- “延迟提交”这个想法已经试过，效果不明显

### 还没做完

- `T2V` 的批量对比还没正式推进
- 更合理的“候选重排”策略还没上
- 还没有证明 Agent 在这个任务上真的能提升 recall

## 6. 当前最合理的下一步

如果继续往下做，我认为最值得试的方向不是继续调“什么时候提交”，而是：

### 让 Checker 一次看一组候选，而不是逐个判断

也就是：

- 先取 `top-k` 候选
- 把它们一起交给 Omni
- 让它直接在一组候选里选“最像的那个”

这比现在的做法更接近真正的“重排”（rerank）。

“重排”这个词的意思很简单：

> 第一轮先粗筛出一批候选，第二轮再把这批候选重新排一遍顺序。

从现在的数据看，这个方向比继续调提交时机更值得试。

## 7. 一句话总结

截至 2026-04-16，这个项目最大的进展不是“指标已经做出来了”，而是：

> 我们已经把项目从一条错误的技术路线，拉回到了论文原始方法上，并完成了端到端实验链路；但当前版本的 Agent 还没有带来实际指标提升，下一步需要从“逐个判断”走向“候选重排”。
