# 项目总结：极简双向检索 Agent（2026-04-15）

## 1. 这个项目现在到底在做什么

这个项目的目标，是做一个**尽量简单、但后面可以继续训练和扩展**的视频检索系统。

它现在主要分成两部分：

1. **检索器（Retriever）**  
   作用是：  
   - 输入一句文字，找最相关的视频  
   - 或者输入一个视频，找最相关的文字

2. **检查器（Omni Checker）**  
   作用是：  
   - 不直接相信检索结果  
   - 再用一个能看视频的模型去“看一眼”，判断这个结果靠不靠谱  

这里面有几个术语，简单解释一下：

- **T2V** = Text-to-Video  
  就是“文字找视频”

- **V2T** = Video-to-Text  
  就是“视频找文字”

- **Agent**  
  这里不是一个很复杂的大系统，而是一个小控制器。  
  它会决定：
  - 先检索
  - 要不要检查结果
  - 如果不满意，要不要改一下查询再检索一次
  - 最后选哪个结果提交

- **Feature / Embedding（特征 / 向量）**  
  这是把一段文字、一个视频，或者一段音频，压缩成一串数字。  
  这些数字本身人看不懂，但模型可以用它们来算“像不像”“像多少”。

你可以把它理解成：

> 我们不是直接拿原始视频和原始文字去硬比，而是先把它们变成统一格式的数字，再去比较这些数字之间的相似度。

---

## 2. 项目的整体设计

这个项目现在是一个**极简版的双向检索 Agent**，结构不复杂，主要代码只有几块：

- `app/retriever.py`  
  负责读取特征、做检索、算基础指标

- `app/omni_checker.py`  
  负责调用 `Qwen2.5-Omni`，让模型去看视频内容，再给出结构化判断

- `app/agent_loop.py`  
  负责单条 case 的决策流程，比如：
  - 第 1 轮先检索
  - 看 top1 / top2
  - 必要时重试
  - 最后提交

- `app/eval.py`  
  负责把 baseline、单条 case、批量 case 串起来执行

- `app/build_feature_dir.py`  
  负责把外部导出的 embedding 和 MSRVTT 的元数据整理成当前仓库能直接读取的格式

这套设计有一个很重要的特点：

> 检索器、检查器、Agent 是拆开的。

好处是：

- 哪一层出问题比较容易定位
- 可以先把某一层打通，再往下一层走
- 后面做强化学习时，也更方便单独替换 Agent，而不是重写整个系统

## 3. 这个项目是怎么一步一步做出来的

### 第一步：先把项目重构成最小骨架

一开始，我们把旧项目停下来，重新搭了一版更小的系统。

目标不是一下子做出完整大系统，而是先保证：

- 代码结构简单
- 单个功能可以单独验证
- 后面能方便接强化学习

所以先做了最基础的几件事：

- `text -> top-k videos`
- `video -> top-k texts`
- baseline 指标
- 单条 agent-case

这一步的重点不是性能，而是**先把主流程站起来**。

---

### 第二步：把 Omni 检查链路打通

这里是整个过程里最费时间的一段。

一开始遇到的问题很多：

1. **环境不兼容**  
   `vllm`、`vllm-omni`、`torch`、`transformers` 之间版本打架  

2. **服务能起，但请求格式不对**  
   一开始用错了多模态请求格式，比如：
   - `type="video"`
   - `type="file"`
   这些都不对

3. **GPU 残留进程占显存**  
   新服务起不来，不是代码错，而是旧服务还占着卡

4. **模型虽然返回了结果，但不是结构化 JSON**

后来我们把问题一点点缩小，最后确认：

- 正确的服务环境要单独重新建
- 要用空闲 GPU
- 请求格式要对齐官方 example client
- 本地视频不能直接乱传，要转成 `video_url`
- 最后还要把 prompt 写得更强，模型才愿意老老实实返回完整 JSON

最终，Omni checker 这一层成功打通了。

服务器上现在已经能稳定做到：

> `OpenAIOmniChecker -> Omni 服务 -> 本地视频 -> 完整 8 字段结构化 JSON`

这一步是整个项目的一个关键节点。

---

### 第三步：解决 feature_dir 缺失问题

Omni 打通之后，接下来最大的阻塞就变成了：

> 没有真实 feature_dir，很多检索逻辑虽然写好了，但没法真正跑

于是后面做了两件事：

1. 写了 `build_feature_dir.py`  
   它的作用是把外部导出的 embedding 整理成当前项目需要的格式

2. 在服务器上排查并尝试导出真实特征  
   最后用 AVIGATE 相关模型代码导出了：
   - `text_embeddings.npy`
   - `video_visual_embeddings.npy`
   - `text_rows.jsonl`
   - `video_rows.jsonl`

当前还没成功的是：

- `video_audio_embeddings.npy`

也就是说：

> 现在文字特征和视频视觉特征已经有了，音频特征还没有完全接上。

---

### 第四步：补上 T2V 所需的文本编码脚本

`V2T` 比较容易，因为输入本来就是视频，可以直接用视频向量查文字。

但 `T2V` 还有一个额外要求：

> 输入是一句原始文字，这句文字也必须先编码成和检索器同一个空间里的向量。

所以后面又补了一个最小脚本：

- `encode_text_avigate.py`

它做的事情很简单：

- 从标准输入读入一行文字
- 用 AVIGATE 的文本编码逻辑把它变成 512 维向量
- 输出成 JSON

这个脚本的意义很大，因为它把：

- 当前仓库里的 `SubprocessTextEncoder`

和

- 服务器上的真实模型编码能力

真正接起来了。

### 4.1 Feature 目录已经真实可用

服务器上已经拿到了一个真实的 feature 目录：

- `text_embeddings.npy`: `(9940, 512)`
- `video_visual_embeddings.npy`: `(497, 512)`
- `text_rows.jsonl`
- `video_rows.jsonl`
- `build_summary.json`

其中：

- `497` 对应 `MSRVTT JSFUSION test split` 里的视频数
- `9940` 对应对应文本数

这说明：

> 数据格式已经不是“假想状态”，而是已经和真实数据集对上了。

---

### 4.2 baseline 已经能跑

当前 baseline 结果是：

```json
{
  "dataset": "MSRVTT",
  "video_count": 497,
  "text_count": 9940,
  "audio_available": false,
  "t2v": {
    "R@1": 0.002,
    "R@5": 0.0116,
    "R@10": 0.0206
  },
  "v2t": {
    "R@1": 0.004,
    "R@5": 0.0101,
    "R@10": 0.0201
  }
}
```

这里也解释一下：

- **R@1 / R@5 / R@10**  
  就是“正确答案有没有出现在前 1 / 前 5 / 前 10 个结果里”

当前这个 baseline 分数比较低，这是正常的，因为：

1. 现在用的是简化版导出链，不是完整论文级实现
2. 还没有音频特征
3. 还没有做进一步调优

所以这个结果的意义是：

> 它证明真实 feature 检索已经能跑，不代表方法已经达到很强的性能。

---

### 4.3 单条真实 V2T agent-case 已经跑通

服务器上已经成功跑通了一个真实的 `V2T agent-case`。

输入视频：

- `video6968`

这个 case 的流程是：

- 第 1 轮先检索
- 检查 top 结果
- 再做一次 retry
- 最后在第 3 轮提交结果

它说明：

> “视频 -> 检索文本 -> Omni 检查 -> Agent 决策 -> 提交”  
> 这条完整链路已经跑通了。

虽然当前没有拿到 `success=true/false` 这种明确离线评估值，但它已经不是 mock 了，而是**真实端到端流程**。

---

### 4.4 单条真实 T2V agent-case 也已经跑通

更重要的是，后面 `T2V` 也跑通了。

示例 query：

- `"a woman is cooking in a kitchen"`

这个 case 的流程是：

- 第 1 轮先检索视频
- Omni 检查 top 候选
- 第 2 轮会把 query 改写得更明确
- 第 3 轮提交结果

这说明：

> “文字 -> 编码 -> 检索视频 -> Omni 检查 -> 改写 query -> 再检索 -> 提交”  
> 这条链路也已经跑通了。

这一步很重要，因为它代表：

- `V2T` 不是唯一跑通的一边
- `T2V` 也已经不是“纸上设计”，而是可以真实执行了

## 5. 这个项目里最难的地方是什么

如果用最容易懂的话来说，最难的地方不是“写代码”，而是**把几条链真正接上**。

### 难题 1：模型服务能不能真的看视频

一开始最大的难题是：

> 模型服务到底能不能真的吃进去本地视频，并返回可用结果

看起来像是一个小问题，但实际上卡了很多层：

- 环境版本
- 显存占用
- 服务启动参数
- 多模态请求格式
- 本地视频如何传给接口

**解决方法：**

- 不再盲猜
- 直接对齐官方 example client
- 先把最小链路跑通
- 然后再把仓库里的 checker 改成同样格式

这个思路后来是对的。

---

### 难题 2：模型不愿意按要求返回结构化结果

链路打通后，又出现一个新问题：

> 模型虽然返回了结果，但只回 `{"is_match": true}`

这不够，因为 checker 需要更多字段，比如：

- `confidence`
- `visual_match`
- `audio_match`
- `main_events`
- `reason`

**解决方法：**

- prompt 里明确说“8 个字段都必须返回”
- 直接写明 `{"is_match": true}` 这种回答是无效的
- 给出完整 JSON 示例
- 在代码里补一层防护：如果字段缺失，要显式标出来

这一步做完后，模型终于开始返回完整 8 字段 JSON。

---

### 难题 3：feature 格式和真实导出链对不上

另一个难题是：

> 代码里需要 feature_dir，但服务器上并没有现成完全对口的目录

一开始其实能找到一些模型、一些 embedding、一些脚本，但都不是当前仓库可以直接读取的格式。

**解决方法：**

- 不再死等“现成目录”
- 先写一个自己的 `build_feature_dir.py`
- 把磁盘格式先钉死
- 再让服务器把真实 embedding 导出来往里放

这样做的好处是：

- 先把格式问题解决
- 后面不管是 AVIGATE 还是别的模型，只要能导出 embedding，就能接到这个系统里

---

### 难题 4：T2V 比 V2T 多了一层文本编码

`V2T` 可以直接从视频向量开始。  
但 `T2V` 输入是一句自然语言，这句话要先变成向量。

这就带来一个问题：

> 文字怎么编码，才能和当前 feature_dir 里的文本向量在同一个空间里？

**解决方法：**

- 写了一个最小 `encode_text_avigate.py`
- 让它通过标准输入/输出与主系统连接
- 这样当前仓库里的 `SubprocessTextEncoder` 就能直接调用它

这一步不是最漂亮的方案，但很实用，也足够支持当前实验。

---

## 6. 整个项目目前的优点和不足

### 优点

1. **结构简单**
   - retriever
   - checker
   - agent loop
   - eval
   这几层分得比较清楚

2. **可观察性强**
   - 每一步都能看日志
   - 单条 case 能看 trace
   - 出错时比较容易定位是哪一层的问题

3. **已经具备后续训练接口**
   - agent 的动作和流程已经形成
   - 后面接强化学习时，不需要重写一整套系统

4. **已经完成真实单条 case 验证**
   - 不是只在 toy data 或 mock 环境里运行

### 不足

1. **音频特征还没接上**
   - 现在 `audio_available = false`
   - 所以当前系统主要还是依赖视觉和文本

2. **baseline 还比较弱**
   - 说明特征和编码链还不是最终成熟版本

3. **一些关键脚本还在服务器临时目录**
   - 例如导出和文本编码脚本
   - 后面需要正式收回仓库

4. **当前更多是“跑通”，还不是“性能优化”阶段**
   - 现在更像打地基
   - 还没到真正做大规模实验对比的时候

## 7. 现在项目最真实的阶段判断

如果不用太多术语，最贴切的说法是：

> 这个项目现在已经不是“概念设计”了，也不是“只有本地单元测试”的阶段。  
> 它已经具备了真实数据、真实视频、真实模型服务、真实单条 case 的闭环能力。

但它也还没有到：

> “已经做完正式实验、可以稳定汇报最终结果”的阶段。

它现在最像的是：

> 一个关键链路已经全部打通、接下来该从单条验证过渡到小规模实验的原型系统。

---

## 8. 我建议的下一步

我认为接下来最合理的顺序是：

### 第一步：把服务器临时脚本收回仓库

至少要把这类能力正式纳入仓库：

- feature 导出脚本
- text encoder 脚本

原因是：

- 现在它们在服务器临时目录里
- 能跑，但不够稳定
- 后面很容易漂移

### 第二步：做小规模 batch

先不要一上来全量跑。

建议先：

- 小规模 `V2T batch`
- 小规模 `T2V batch`

先验证：

- 稳定性
- trace 质量
- checker 输出质量

### 第三步：再考虑更正式的实验和文档

到那一步再做：

- 更完整的 baseline 对比
- 更系统的结果分析
- RL 数据导出

---

## 9. 最后一句总结

这个项目目前最重要的成果，不是某个数字指标，而是：

> 我们已经把“检索 + 视频检查 + agent 决策”这条真实链路打通了。

这意味着后面的工作，不再是“想办法让系统活过来”，而是：

> 让这个已经活起来的系统，变得更稳定、更完整、更能做实验。
